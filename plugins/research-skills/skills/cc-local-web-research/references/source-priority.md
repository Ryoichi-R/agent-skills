# 情報源の優先順位と信頼性評価基準

## 優先順位（高い順）

| 順位 | 情報源                     | 説明                                              |
| ---- | -------------------------- | ------------------------------------------------- |
| 1    | 公式ドキュメント・一次情報 | RFC、公式リファレンス、公式ブログ、リリースノート |
| 2    | ローカル資料（最新）       | skill-source 内の資料で、更新日が直近のもの       |
| 3    | 信頼性の高い二次情報       | 技術書、査読付き論文、著名な技術ブログ            |
| 4    | ローカル資料（古い）       | skill-source 内の資料で、更新日が古いもの         |
| 5    | 一般的なWeb情報            | Stack Overflow、Qiita、個人ブログ等               |

## 信頼性評価のルール

### 鮮度の重要性

- **時点依存の話題**（価格、バージョン、API仕様、ニュース）: 発行日・更新日を必ず明記する
- ローカル/Webとも原文の公開日・改訂日・適用日を比較する。`modifiedAt` と取得日は保存/取得時点として分離する。日付不明はunknownとし、新しいmtimeだけで優先しない
- 1年以上前の情報は「古い可能性あり」と注記する

### 矛盾解消の手順

1. **情報源の権威性を比較**: 公式 > 非公式、一次情報 > 二次情報
2. **鮮度を比較**: 新しい情報を優先（ただし、一次情報の古い記述が二次情報の新しい解釈より正確な場合あり）
3. **複数Web情報の一致度を確認**: 複数の独立した情報源が一致する場合は信頼性が高い
4. **判断を明記**: どちらを採用し、なぜそちらを選んだかを回答に記載する

### ローカル資料の特別扱い

- ローカル資料は**組織固有の文脈**を含む可能性がある（社内ルール、カスタム設定等）
- 一般的な技術情報についてはWeb情報を優先するが、組織固有の設定・手順についてはローカル資料を優先する
- ローカル資料とWeb情報が矛盾する場合は、矛盾点を明記した上で両方の情報を提示する

### 深堀りローカル情報の扱い

- 深堀りローカル情報（ステップ3で取得）は、通常のローカル資料（ステップ1で取得）と同じ優先順位で扱う
- 発見経路が異なるだけで、情報源としての性質は同一である
- 矛盾解消時はステップ1のローカル情報と同等の信頼性として評価する

## 資料ルート内の参照順指定

任意の `.research-policy/source-preferences.json` は、利用者が確認した文書の関係を記録するローカルデータ。隠しディレクトリのため検索本文には混入しない。原本の移動・削除や版の自動判定は行わない。

```json
{
  "schema_version": "1.0",
  "groups": [
    {
      "id": "training-topic",
      "documents": [
        {
          "path": "current.md",
          "sha256": "<64桁のSHA-256>",
          "role": "preferred",
          "edition": "確認した改訂年月",
          "note": "この論点の優先資料"
        },
        {
          "path": "legacy/related.md",
          "sha256": "<64桁のSHA-256>",
          "role": "related_date_unknown",
          "edition": "不明",
          "note": "関連資料。同一文書の旧版とは未確定"
        }
      ]
    }
  ]
}
```

- `path` は資料ルートからの相対パス。各グループに `preferred` が必要。同じパスの重複登録、ルート外、リンク、秘密情報のパス、文書ハッシュ不一致、不正な設定は `source_preference_invalid` で停止する。
- `role` は `preferred` / `related_older` / `related_date_unknown`。`edition` と `note` は各256文字以内の単一行。`related_older` も同一文書の旧版を意味せず、確認できた年代の古い関連資料として扱う。
- 優先資料は、原文に検索語（空白で区切った語のいずれか）がリテラル一致した場合だけ先へ返す。Indexedの候補上限適用前と最終返却前、FullTextのページ分割前に適用する。他資料同士の相対順と関連度スコアは維持する。関連度順位と情報源の権威性は別に評価する。
- Indexedでは、優先資料に原文一致があれば、上位頻出語の索引にその語がなくても候補に追加する。対象はハッシュで束縛した優先資料のみ。原文が一致しない資料や索引に存在しない資料は追加しない。
- 版・関係は既存出力の `message` に記録する。スニペットと出典行番号は原文のまま。設定のない資料ルートの検索動作は従来どおり。
- 旧版・時点指定の検索は `-IgnoreSourcePreference` で並べ替えを無効にできる。資料名・低頻度語を索引の頻出語に依存せず確認する場合は `-SearchMode FullText` を併用する。FullTextのfingerprintには設定ハッシュとこの選択を含める。
- 文書を更新した場合は利用者が関係と版を再確認し、ハッシュを更新して再索引する。ファイルの保存日時から自動昇格しない。

## 現行性の外部照合記録

`.research-policy/currentness.json` は資料本文を変更せず、確認日、照合報告書、対象文書のSHA-256、論点別の判定・回答時の扱い・出典を登録する任意のローカルデータ。形式は [currentness-policy.schema.json](currentness-policy.schema.json) に従う。

- `schema_version`: `1.0`。`checked_at`: タイムゾーン付き確認日時。
- `report`: `{path, sha256}`。`documents`: 同形式の配列。パスは資料ルートからの相対パス。
- `findings`: `id`, `status`, `topic`, `action`, `local_statement`, `official_current_or_comparison`, `note`, `keywords`, `locations`, `sources` の配列。`locations` は `{path, line}`、`sources` は `{title, url, basis}`。具体的な資料の値をこのリポジトリの例やテストに転記しない。

検索語に `keywords` のいずれかが含まれる、または返却資料が `locations` に含まれる場合、その判定と出典を既存の `message` にJSONで添える。ヒット文書に登録された全論点を添えるため、短いスニペットだけから現行性を判断しない。照合記録から検索ヒットを捏造せず、スコア・本文・行番号・件数・ページングは変えない。該当なしの検索に注意情報だけ付く場合も、`status: empty` と `matches: []` は維持する。

検索ごとに設定と束縛文書・報告書を検証し、索引TTL内の更新も反映する。旧版検索の `-IgnoreSourcePreference` でも現行性確認は無効化しない。FullTextのfingerprintにも設定ハッシュを含める。2MBを超える記録、未登録の出典位置、重複ID・パス、ルート外・リンク・秘密情報パス、ハッシュ不一致、不正な設定は `currentness_policy_invalid` として停止する。

確認日は恒久の有効期限ではない。公式資料の適用期間・官署・対象契約・例外を回答時点で確認する。確認できない内部基準を、一般法令や他省庁の数値から推定して確定扱いしない。
